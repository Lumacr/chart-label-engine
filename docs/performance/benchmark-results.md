
# Performance Benchmark Results

## 1. Overview

This document records the initial performance baseline for Chart Label Engine.

The benchmarks evaluate the main application components and the greedy placement optimizer using deterministic input data.

The purpose is to:

- Establish a reproducible performance baseline.
- Understand how execution time scales with input size.
- Identify components that may become performance bottlenecks.
- Document opportunities for future optimization.

These measurements represent one execution environment and a specific set of benchmark scenarios. They are not universal performance guarantees.

## 2. Benchmark Environment

The benchmarks were executed on:

- Operating system: macOS
- Compiler: AppleClang 21.0.0.21000101
- C++ standard: C++20
- Build configuration: Release
- Benchmark framework: Google Benchmark v1.9.1
- CPU configuration reported by Google Benchmark: 12 x 2600 MHz
- CPU caches reported by Google Benchmark:
  - L1 Data: 32 KiB
  - L1 Instruction: 32 KiB
  - L2 Unified: 256 KiB (x6)
  - L3 Unified: 12288 KiB

The exact CPU model and other environmental details were not independently recorded.

The benchmark executable was built using CMake with:

```bash
cmake -S . -B build-benchmarks \
    -DCMAKE_BUILD_TYPE=Release \
    -DBUILD_TESTING=OFF \
    -DBUILD_BENCHMARKS=ON

cmake --build build-benchmarks --config Release --parallel
```

## 3. Benchmark Methodology

### 3.1 Input Data

All benchmarks use deterministic synthetic data generated by `benchmark_data.hpp`.

The generated data has the following characteristics:

- Label dimensions: 40 x 12 units.
- Grid spacing: 100 units.
- Grid columns: 25.
- Plot area: 3000 x 3000 units.
- Labels and anchors are generated in a regular grid.
- Placement labels match their corresponding chart targets.

The placements used by the collision detector and placement scorer are centred on their respective anchors.

The generated placements do not overlap and remain inside the plot area.

This provides a controlled baseline, but does not represent dense or highly constrained chart layouts.

### 3.2 Timed Operations

Input data and component instances are prepared before entering the benchmark iteration loop whenever possible.

The timed operations are:

- `CandidateGenerator`: generates eight candidate placements for every chart target and collects the results in a vector.
- `CollisionDetector`: detects collisions across the complete placement vector.
- `PlacementScorer`: evaluates the complete placement vector against its chart.
- `GreedyPlacementOptimizer`: optimizes the complete chart and returns the resulting placements.

The candidate generation benchmark includes result-vector allocation and collection. Its measurements therefore represent the complete generation workload rather than only the internal candidate-generation calculations.

The benchmarks report processed labels through Google Benchmark's `SetItemsProcessed`. This counter represents labels processed, not the number of pairwise collision comparisons.

### 3.3 Measurement Configuration

Each scenario was executed with three repetitions.

All benchmark groups were executed with `--benchmark_min_time=0.2s` and `--benchmark_repetitions=3`. No configuration warnings were reported during the final component benchmark run.

Reported values below use the median execution time across the three repetitions. Medians are used to reduce the influence of individual measurement variations.

## 4. Results

All execution times below are medians from three repetitions.

### 4.1 CandidateGenerator

- 10 labels: 2.912 microseconds
- 50 labels: 11.733 microseconds
- 100 labels: 28.156 microseconds
- 500 labels: 151.205 microseconds

The observed execution time grows approximately linearly with the number of labels.

Increasing the input size from 100 to 500 labels increases execution time by approximately 5.37 times.

This is consistent with the expected O(n) complexity: each target is processed independently and produces a fixed number of candidates.

Candidate generation is not a significant bottleneck in the measured scenarios.

### 4.2 CollisionDetector

- 10 placements: 0.894 microseconds
- 50 placements: 26.410 microseconds
- 100 placements: 92.745 microseconds
- 500 placements: 2.226 milliseconds

The observed execution time grows approximately quadratically with the number of placements.

The detector compares every pair of placements, resulting in:

O(n²)

pairwise comparisons.

Increasing the input size from 100 to 500 placements increases execution time by approximately 24.0 times, which is close to the 25-fold increase expected from quadratic scaling.

Collision detection is a significant performance cost for larger inputs.

### 4.3 PlacementScorer

- 10 placements: 1.688 microseconds
- 50 placements: 27.589 microseconds
- 100 placements: 107.550 microseconds
- 500 placements: 2.408 milliseconds

The scorer exhibits approximately quadratic scaling.

This is expected because scoring invokes collision detection and additionally evaluates boundary penalties and anchor distances.

The collision detector accounts for the dominant computational cost as input size increases.

### 4.4 GreedyPlacementOptimizer

- 10 labels: 137.056 microseconds
- 25 labels: 1.490 milliseconds
- 50 labels: 9.001 milliseconds
- 100 labels: 76.639 milliseconds

The optimizer is the most computationally expensive component in the measured scenarios.

Its current implementation:

1. Generates eight candidates for each target.
2. Initializes each label with its first candidate.
3. Evaluates the complete solution.
4. Iterates over labels and evaluates alternative candidates.
5. Accepts strict improvements.
6. Repeats until a complete pass produces no improvements.

Each candidate evaluation recalculates the complete placement score.

Since scoring includes an O(n²) collision detection operation and the optimizer evaluates approximately eight candidates per label, one optimization pass has an approximate O(n³) cost.

The number of passes depends on the input data and optimization behaviour.

The measured growth is consistent with this expected complexity. Doubling the input from 50 to 100 labels increases median execution time by approximately 8.5 times.

The 100-label scenario takes approximately 76.6 milliseconds on the recorded environment.

## 5. Performance Analysis

The measurements identify the following characteristics:

- Candidate generation scales approximately linearly and has a relatively low execution cost.
- Collision detection scales quadratically because all placement pairs are examined.
- Placement scoring inherits the quadratic cost of collision detection.
- The greedy optimizer amplifies scoring costs by repeatedly evaluating complete solutions.

The primary performance bottleneck is therefore the repeated full-solution evaluation performed by the greedy optimizer.

The collision detector is the main source of computational cost within an individual score evaluation.

## 6. Limitations

These results should be interpreted within the limits of the benchmark design.

### 6.1 Synthetic Data

The benchmark data uses a regular grid with evenly spaced labels and anchors.

The collision detector and scorer scenarios contain no overlapping placements.

Real chart layouts may contain dense clusters, overlapping candidates, irregular anchor distributions, and placements outside the plot area.

### 6.2 Single Execution Environment

The measurements were collected on one machine and one compiler configuration.

Results may differ across processors, operating systems, compilers, build configurations, and system load conditions.

### 6.3 Repetition Count

Each scenario was measured three times.

This is sufficient for an initial baseline, but a larger number of repetitions would provide stronger statistical confidence.

### 6.4 Optimizer Behaviour

The optimizer measurements use a controlled dataset in which the initial North candidate is locally optimal.

These results do not represent all possible optimization paths or the worst-case number of passes.

### 6.5 Scaling Interpretation

Observed scaling is consistent with the theoretical complexity of the current implementations.

It does not constitute a formal proof of complexity or a guarantee of execution time for arbitrary input data.

## 7. Future Optimization Opportunities

The following opportunities have been identified for future investigation:

### 7.1 Incremental Placement Scoring

The optimizer currently recalculates the complete score whenever one placement changes.

An incremental scoring approach could update only the contributions affected by the modified placement:

- Collisions involving the changed placement.
- Boundary penalty for the changed placement.
- Anchor distance for the changed placement.

This could reduce the cost of evaluating an individual candidate from O(n²) to O(n), potentially reducing one optimization pass from approximately O(n³) to O(n²).

Such an implementation must preserve the exact lexicographic ordering of `PlacementScore`, deterministic behaviour, and existing validation guarantees.

### 7.2 Spatial Collision Detection

The current collision detector examines every placement pair.

Spatial partitioning or spatial indexing could reduce the number of comparisons for sparse layouts.

Potential approaches include uniform grids, spatial hashing, and tree-based spatial indexes.

These approaches should only be introduced after measuring representative dense and sparse scenarios.

### 7.3 Additional Benchmark Scenarios

Future benchmarks should investigate:

- Dense layouts with overlapping placements.
- Placements outside plot boundaries.
- Irregular anchor distributions.
- Different label dimensions.
- Optimizer workloads requiring multiple improvement passes.
- Larger input sizes.

### 7.4 Rendering Performance

SVG rendering is not included in this initial benchmark baseline.

A dedicated benchmark may be added if rendering performance becomes relevant.

## 8. Conclusion

The initial benchmark results confirm that the core components behave consistently with their expected computational complexity.

Candidate generation has a low, approximately linear cost.

Collision detection and placement scoring exhibit quadratic scaling.

The greedy optimizer is the main performance bottleneck because it repeatedly evaluates complete solutions.

The current implementation provides a useful baseline for future optimization work. Incremental scoring is the most promising area for further investigation, but no structural optimization is justified solely by these initial measurements.

Future changes should be supported by additional benchmarks and regression tests.
